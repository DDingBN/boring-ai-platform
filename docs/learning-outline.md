## 1. 学习目标与安排

核心主题：从一条普通聊天请求开始，逐步学会构建可靠、可控制、可追踪的 AI 应用。

贯穿场景：用户在聊天页面咨询模拟订单，助手查询订单；需要进一步处理时，提出创建工单的
建议，经用户批准后执行。订单和工单均使用本地模拟数据。

完成必修后，应能解释并实现：

- 一条消息如何经过页面、HTTP 接口、业务服务和模型适配层，并返回页面。
- 回复如何逐步显示；停止、超时与失败如何影响前后端状态。
- 会话历史如何保存，以及如何把需要的历史交给模型。
- 重试、重复提交和并发请求如何避免产生重复或错乱的数据。
- Agent 如何请求调用工具，程序如何检查参数、权限和执行限制。
- 有副作用的操作如何审批、暂停、恢复，并避免重复执行。
- 如何通过测试、执行记录和固定问题集判断功能与改动是否有效。

### 1.2 起点检查与补课规则

Python、后端和 SQL 均从基础讲起，不作为入学条件。前端和工具基础通过下面的小检查确认：

- 能否读懂 JavaScript 的函数、对象、数组与基本 `async/await`？
- 能否在编辑器中打开文件，在指定目录运行命令？
- 能否查看 Git 差异，区分自己的修改与已有修改？
- 能否找到浏览器 Console、Network 和服务端终端？

不会的项目记为“待补”，在首次使用前完成一个带示范的小练习；不能只让学习者自行查资料。
HTTP 在 D01、D06～D07 教；Python 在 D02～D05 教；SQL 与事务在 M07～M08 前半段教。
类、异步、测试替身、依赖注入均在使用前解释，不能因为现有代码用了就默认学习者已经懂。

### 1.3 学习主线与现有问题的处理

第一天只观察 **一次发送、一次后端处理、一次响应和页面更新**，建立请求与响应的概念。
完整代码追踪安排在掌握 Python 和接口基础之后；不要求第一天跨七个文件独立阅读。

学习任务由能力目标决定。现有代码的问题先区分为缺陷、尚未实现的功能和有意的设计选择；
缺陷单独记录、修复，不能因为它恰好存在就包装成入门必学题。
当前未实现多轮上下文只在项目现状中注明。“连续两轮对话”实验放在 M11，
用于验收新实现的上下文能力，不是 D01 的作业，也不要求初学者证明系统没有记忆。

## 2. 当前起点与项目约定

以下为迁入仓库时核对的实现起点，课程中的后续能力仍需实际完成。学习验收位置见
[学习交接](handoff.md)，完整能力与待办以 [项目进度](project-status.md) 为准。

| 内容     | 当前真实状态                                                    | 后续方向                          |
| -------- | --------------------------------------------------------------- | --------------------------------- |

| 检查     | 4 个业务接口测试＋4 个入门练习测试；Web 有 lint，暂无自动化测试 | 随功能补充各层测试                |

术语先认用途：Provider 是项目中负责模型调用的适配代码；Mock 是本地模拟实现，当前只回显
收到的文字；Service 是组织业务处理的代码。D08 才系统学习这些分工。

下面是开发阶段使用的约定，不是第一天需要背诵的知识：

1. 调用链保持 `Vue → FastAPI`。路由处理 HTTP，Service 处理业务，`llm` 适配模型。
2. 保持 `/api/v1`、普通 JSON 的 `{ code, msg, data }` 和 `x-request-id` 兼容。
3. SSE 使用独立事件契约，不能交给现有 Axios 普通 JSON 解包器处理。
4. 开发与自动化默认 Mock 或脚本化测试模型，不发送真实 DeepSeek 请求。
5. 引入用户数据时明确服务端可信身份。前端携带 token 不等于已有服务端认证。
6. 数据库设计目前尚未落地，RunStep、工具消息和审批状态在对应模块先补设计再实现。
7. API、数据库和实现状态发生变化时，同步相应项目文档。临时教学例子不冒充项目功能。
8. 当前根命令 `pnpm lint` 只覆盖 Web，`pnpm test` 只覆盖 Server；Server 尚无 lint 脚本。

## 3. 每次学习怎样进行

### 3.1 每天 4～6 小时的使用方式

| 环节           | 基础时长 | 要完成的事                       |
| -------------- | -------- | -------------------------------- |
| 回顾与先修检查 | 30 分钟  | 复述上次结果，确认今天用到的知识 |
| 概念与小示例   | 60 分钟  | 围绕一个问题解释，再运行最小例子 |
| 独立尝试       | 90 分钟  | 按提示完成一个范围明确的任务     |
| 审查与验证     | 45 分钟  | 解释代码，观察正常与失败情况     |
| 记录与接续     | 15 分钟  | 记录证据、疑问和下次起点         |

以上合计 4 小时，可分段完成。额外 1～2 小时用于重做、排错和巩固；理解稳定后再进入下一
学习单元。一个模块可以跨多天，一天也可以完成两个较小单元；不因为空出时间而跳过先修。

### 3.2 每个学习单元必须交代的内容

带学时按以下顺序展开。后面的模块给出路线，开课时还必须把对应小任务具体化：

1. **问题**：今天要理解或实现什么，为什么现在学。
2. **先修**：只使用已经讲过的知识；发现缺口，先补一个小例子，并说明与目标的关系。
3. **必要概念**：首次出现的术语用普通话解释；给一个能运行的最小示例，逐行说明。
4. **执行位置**：指出具体文件、命令执行目录和运行命令，说明文件已有还是需要新建。
5. **任务边界**：明确哪些代码已提供、哪些由学习者完成、预期输入输出是什么。
6. **提示与尝试**：先给方向，卡住时再给结构或局部示例；不提前代写完整作业。
7. **审查与解释**：学习者贴代码或观察记录后，再审查并解释原因。
8. **验证**：先正常情况，再选一个相关失败情况；观察课允许用操作记录，学过测试再要求写测试。
9. **结论**：用代码、输出或测试结果说明完成了什么，不能只凭“看懂了”勾选。

不能把“先给提示”理解为只给一个陌生类名让学习者猜。示例是起点，作业应是已经解释过的
知识的一次小变化。调整任务要说明原因、保留的学习目标以及验收变化，不能临时换成无关练习。

## 4. 阶段 A：从零入门，读懂单条聊天请求

预算：10～12 个学习日。默认依次完成 D01～D12；先修通过才合并，不跳过知识依赖。

### D01：观察一条请求怎样返回结果

- 问题：点发送后，浏览器发出了什么，收到的内容怎样对应页面？
- 先修：会打开项目和终端；不会使用 Network 时先由带学者示范一次。
- 必要概念：浏览器与服务端、请求方法和地址、JSON 请求体、HTTP 状态码、响应体。
- 位置：现有 Chat 页面和浏览器 Network；暂时只定位 `ChatPage.vue` 的发送函数。
- 起步：按第 14.2 节启动 Mock，发送一条“你好”，找到对应 POST 请求。
- 小任务：记录地址、方法、请求中的文字、响应中的助手文字，并与页面对应。
- 失败观察：请求不存在的接口，比较成功与 `404` 响应；具体操作见第 14.2 节。
- 完成证据：能用自己的话解释这次发送和返回。无需写 Python、测试或研究会话历史。

### D02：运行第一段 Python

- 问题：后端代码怎样被解释器执行，函数如何接收输入和返回结果？
- 先修：D01；先解释 Python 解释器、`.py` 文件、缩进、字符串和 `print`。
- 位置：已有 `apps/server/learning/day02.py`；在 `apps/server` 执行：

```powershell
.\.venv\Scripts\python.exe learning/day02.py
```

先运行并逐行解释这个起步示例：

```python
def make_reply(content):
    return "收到：" + content

message = {"content": "你好"}
replies = [make_reply(message["content"])]
print(replies[0])
```

预期输出 `收到：你好`。分别解释函数、参数、返回值、字典、列表和索引，不要求一次记住所有语法。
小任务：修改输入文字，让函数给回复加上自己选择的前缀。提示：先找参数从哪里进入函数。
失败观察：把字典键拼错，找到错误末行和对应代码位置；暂不要求自行编写异常处理。

### D03：分支、循环、模块和错误

- 问题：怎样处理不同输入、重复处理数据，并找到错误发生的位置？
- 先修：D02。先解释 `if`、`for`、`import`，再讲 `raise`、`try/except` 和错误堆栈。
- 位置：已有 `learning/day03.py`、`learning/text_helpers.py`；运行前者的方式同 D02。
- 起步：带学者把 D02 的函数移到 `text_helpers.py`，示范一次导入与调用。
- 单元 1：用循环处理列表中的两条独立文字，打印各自结果。这是语法练习，不是多轮聊天。
- 单元 2：解释 `strip()`，在函数里识别空白输入；先观察 `ValueError`，再在调用处捕获它。
- 小任务：普通文字返回回复，空白文字给出明确提示。先只改一个条件分支。
- 正常/失败：`"你好"` 正常；`"   "` 进入错误分支；能说明抛出与捕获分别在哪一行。

### D04：类和对象怎样保存自己的数据

- 问题：为什么项目中有 `class`，`self` 指的是什么？
- 先修：函数、字典、导入。先示范类、实例、`__init__`、实例属性和方法调用。
- 位置：已有 `learning/day04.py`；再阅读现有 `app/llm/mock.py`。
- 起步例子：一个 `Echo` 类在初始化时保存前缀，方法接收文字并返回“前缀＋文字”。
- 小任务：创建前缀不同的两个实例，检查它们各自的结果；不接入业务代码。
- 提示：前缀属于对象，输入文字是每次调用方法的参数。
- 正常/失败：两个实例的前缀不串用；漏传必要初始化参数时能定位调用错误。
- 补充：给已理解的参数加 `str` 注解；说明注解主要表达预期类型，不等于 HTTP 请求校验。

### D05：理解等待与清理

- 问题：等待耗时操作时，`async`、`await` 和 `finally` 分别做什么？
- 先修：D03 的异常与 D04 的方法调用。
- 位置：已有 `learning/day05.py`，使用项目解释器直接运行。
- 起步：带学者给出 `async def` 函数，用 `await asyncio.sleep(0.2)` 模拟等待，
  通过 `asyncio.run(...)` 调用；讲清普通返回值与等待异步函数结果的区别。
- 小任务：打印“开始”“得到结果”“清理”，观察顺序；在等待后的指定位置模拟一次异常。
- 正常/失败：成功能得到结果；失败也执行 `finally` 中的清理提示，不伪装成成功。
- 本单元先理解一次等待，不要求设计并发任务、取消传播或异步生成器，这些在 M04～M06 学。

### D06：写一个最小 HTTP 接口

- 问题：浏览器请求一个地址，怎样找到并调用 Python 函数？
- 先修：函数、导入、类和基础等待；先解释 FastAPI 应用、路由以及 `@app.get` 的注册作用。
- 位置：已有 `learning/__init__.py` 和 `learning/day06_api.py`，使用独立端口 3002。

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/hello")
def hello():
    return {"message": "你好"}
```

在 `apps/server` 执行：

```powershell
.\.venv\Scripts\python.exe -m uvicorn learning.day06_api:app --reload --port 3002
```

先访问 `http://127.0.0.1:3002/hello`，预期得到 `{"message":"你好"}`。
再由带学者示范一个用 Pydantic `BaseModel` 接收 `content` 的 POST `/echo`，
解释 JSON 到 Python 字段的转换，通过 `http://127.0.0.1:3002/docs` 操作。
小任务：给 POST 回复增加一个已讲过的字段。失败观察：错误地址返回 `404`，错误方法不会进入函数。

- 位置：拟新增 `app/repositories/` 及数据库测试，身份依赖放到现有依赖层。

  2. 用服务端身份依赖提供用户和应用 ID；开发期可用明确限定于开发环境的固定身份。
  3. 会话访问按 `conversationId + userId + appId` 限定，用两个测试身份检查隔离。
  4. 分别实现“保存用户消息与 Run”“保存助手消息并更新成功状态”的短事务。

### M09：执行状态、失败与终态保护（原第 9 课）

- 问题：一次调用正在进行、失败或被取消时，数据库应留下什么？
- 先修：M06、M08；先用表格学状态和允许转换，再讲条件更新与竞争。
- 起步：给一个固定 Run 写出 `queued → running → succeeded`，再单独画失败和取消路径。
- 位置：Run 业务处理、Repository 和对应数据库集成测试。
- 分步任务：
  1. 保存状态与结束时间，先验证成功、失败和取消三条独立路径。
  2. 明确终态不能随意被覆盖；用条件更新保护状态。
  3. 重试创建新的 Run，继续关联原用户消息，避免再创建同一用户消息。
  4. 接回流式链路：助手消息与 Run 成功在同一事务提交后，才发送 SSE 成功结束事件。
  5. 制造取消后迟到成功、助手消息写入失败，检查最终状态与输出一致。
- 正常/失败：只有成功 Run 关联最终助手消息；取消不能被迟到结果改成成功。
- 完成证据：上述故障测试；生成完毕但保存失败时，向客户端报告失败，不宣告业务成功。
- 恢复要求：数据库故障使失败状态暂时无法保存时，要有可核对记录，在恢复后落实终态。

阶段 C 验收：

- [ ] 学习者能解释一条 SQL、一个约束以及一次提交/回滚；不只会复制 ORM 调用。
- [ ] 从空库迁移、初始化和基本读写可复现，自动化使用隔离数据库。
- [ ] 会话读写有归属校验；网络等待不跨数据库事务，失败写入可回滚。
- [ ] 成功、失败、取消有状态与结束时间；迟到结果不能覆盖终态。
- [ ] 数据持久化成功后才发送流式成功事件；Provider 未提供用量时保存未知值，不填成零。

## 7. 阶段 D：历史、上下文与重复请求

预算：4～5 个学习日。目标是刷新后恢复对话，并让重复或并发请求有明确结果。

### M10：先查历史，再处理分页与切换（原第 10 课）

- 问题：怎样取回保存的消息，消息很多或切换会话时怎样避免混乱？
- 先修：M07～M09；补稳定排序、索引与游标的用途。
- 起步：在测试库给同一会话插入 3 条消息，先只查询第一页，核对顺序与归属。
- 位置：规划中的 Conversation 路由、Service、Repository、前端会话列表与历史面板。
- 分步任务：
  1. 实现所需的会话列表、消息历史接口，同步 API 文档；不要一次实现所有占位接口。
  2. 页面加载一个会话的历史，刷新后仍能读到记录。
  3. 引入“时间＋ID”的稳定排序与游标，构造相同时间戳的记录再翻页。
  4. 实现会话切换，防止旧请求晚返回时覆盖新会话内容。
- 正常/失败：静态数据翻页无重复遗漏；无效游标返回明确错误；越权读取被拒绝。
- 完成证据：查询测试、翻页测试、快速切换演示。再讨论按最近活动时间排序时新增消息对翻页的影响。

### M11：实现多轮上下文，再用两轮对话验收（原第 11 课）

- 问题：怎样让本次模型调用使用此前的有效信息？
- 先修：M10、D12；补用户/助手/system 角色、上下文窗口、输入与输出预算。
- 起步：先手工给出“用户说了什么、助手回复什么、本次又问什么”的消息列表，观察角色和顺序。
- 位置：历史查询后的上下文组装函数、Provider 输入接口及记录模型输入的测试替身。
- 分步任务：
  1. 将 Provider 输入从单条文字扩展为有角色的消息序列，保持 Mock 和真实适配的一致约定。
  2. 按可信会话身份读取历史，选择最近的完整有效轮次，并为本次输入和输出留出预算。
  3. 明确失败用户消息是否参与历史；失败或取消的半截回复不冒充成功回复。
  4. 再运行连续两轮对话实验：先发送“我叫小明”，再发送“我叫什么？”，记录第二次实际模型输入。
- 正常/失败：第二次输入包含选定的第一轮有效内容；当前输入只出现一次；无历史、预算不足、失败或取消记录均有确定策略。
- 完成证据：记录输入的替身证明传递正确；如人工体验真实模型，另行明确启用和预算。
- 设计结论：前端可以只发当前文字与会话 ID，由后端加载和组装历史；无需每次由前端上传全部历史。
  Mock 回显不能用来判断真实模型能否理解或记住姓名；两轮实验的自动化结论是输入是否传对。
- 作业：此时再解释前端、Service、数据库、Provider 各自承担的上下文职责。

### M12：重复提交、并发与重启收尾（原第 12 课）

- 问题：同一次提交发了两遍，或者服务重启，怎样避免重复执行和遗留状态？
- 先修：M09 的状态保护、M11 的上下文；补幂等键、唯一约束、同键异参冲突。
- 起步：先在测试中顺序发送两次带相同幂等键的提交，观察它们是否引用同一个 Run。
- 位置：提交接口、Service、数据库唯一约束与并发集成测试。
- 分步任务：
  1. 写清幂等键的身份范围、参数比对和保留策略；“重发”和“重新生成”分别定义。
  2. 相同提交复用原结果；显式重新生成新建 Run，关联原用户消息。
  3. 再做同时请求，落实数据库约束与同会话串行策略，不能仅依赖按钮禁用或进程内存锁。
  4. 执行中重启，识别遗留 Run，并按明确策略结束或进入恢复核对。
- 响应约定：原执行仍在进行时返回已有 Run 标识与状态，结束后返回已有结果；
  同键重发不重新执行，也不自动重放或重新订阅原 SSE，响应形式写入契约。
- 正常/失败：无重复用户消息；同键不同参数明确冲突；并发与重启结果可解释。
- 完成证据：顺序重发、并发重发、异参冲突和进程重启四类验证。

阶段 D 验收：

- [ ] 刷新、切换与分页可复现，归属和无效游标有负向测试。
- [ ] 模型收到选定历史，当前消息不重复，失败与取消内容的选择规则明确。
- [ ] 重复提交与重新生成含义分开，依靠服务端与数据库保护，并能识别遗留执行。
- [ ] 取消后不保存完整助手消息的策略与页面说明一致；分片持久化和断线续传仍留作选修。

## 8. 阶段 E：工具与最小 Agent

预算：4～6 个学习日。目标是助手能使用受约束的只读订单工具，执行过程有记录。

### M13：先写普通订单查询，再包装为工具（原第 13 课）

- 问题：模型怎样使用程序已有的查询能力，又不越过数据权限？
- 先修：函数、请求校验、Service 与可信身份；先解释“工具就是可被请求调用的业务函数”。
- 起步：用字典保存模拟订单 `A100`，先直接调用普通查询函数，再考虑模型。
- 位置：拟新增订单 Service、工具输入输出模型、工具注册模块和对应测试；开课时确定具体文件。
- 分步任务：
  1. 实现普通查询函数，传入订单编号和服务端身份，返回受限的订单信息。
  2. 给函数增加输入输出 Schema，再定义工具名与描述，说明注册表怎样找到对应函数。
  3. 从普通调用接入工具入口，保持同样的校验与归属规则，不暴露任意数据库查询能力。
- 正常/失败：覆盖订单存在、不存在、参数非法、其他用户订单、查询超时。
- 完成证据：业务函数和工具入口均有验证；模型给出的用户 ID 不能扩大权限。

### M14：观察一轮工具调用，再接 Agent 框架（原第 14 课）

- 问题：模型输出工具名和参数后，程序怎样执行并把结果交回？
- 先修：M13、M11 的消息角色；先解释工具调用 ID、工具结果消息和停止条件。
- 起步：使用固定的“请求查询 A100 → 工具结果 → 最终回复”三段数据，手工走通一轮。
- 位置：拟新增 Agent Service；脚本化测试模型先放测试目录，复用前先解释它与回声 Mock 的差别。
- 分步任务：
  1. 给工具请求和结果匹配同一调用 ID，程序检查名称、参数、身份后执行。
  2. 在首次运行可循环流程前设置最大工具次数、总时限和结果长度限制。
  3. 由带学者提供与锁定版本匹配、可运行的脚本化 Chat Model 起点；学习者先改一个返回分支。
  4. 再使用该版本的 LangChain `create_agent` 接入订单工具，记录选择、输入、结果和最终回复。
- 正常/失败：普通问答与查订单均能结束；未知工具、非法参数、工具异常、反复请求工具均有确定结果。
- 完成证据：脚本化模型验证调用对应与停止规则。当前纯文本回声 Mock 不足以证明工具循环正确。
- 边界：外部工具结果是数据，不能修改服务端授权或绕过执行限制；真实选工具质量单独评测。

### M15：记录每一步并展示进度（原第 15 课）

- 问题：一次用户任务中可能有多次模型与工具调用，怎样查到各步结果？
- 先修：M14、M09；先对照一条订单任务列出模型与工具步骤。
- 起步：拿 M14 固定脚本，画出一次任务及其三个步骤，再对应数据库记录。
- 位置：Run/RunStep 模型、迁移、执行 Service、前端进度展示与测试。
- 分步任务：
  1. 明确 Run 是一次用户任务的执行尝试，RunStep 记录各次模型或工具调用，同步设计和迁移。
  2. 补 system/tool 消息结构、工具结果的保存和重放规则。
  3. 保存步骤耗时、结果与错误，将 M14 已有的执行预算与步骤关联。
  4. 页面显示“查询订单中”等进度，不向用户倾倒内部技术细节。
- 正常/失败：每一步可追踪；超限受控结束；步骤失败与最终任务状态一致。
- 完成证据：一条完整任务的执行记录及一条超限记录；Run 总用量与各模型步骤口径一致，未知用量明确标记。

阶段 E 验收：

- [ ] 有界工具循环在成功、工具失败与超限时均能结束。
- [ ] 工具参数、名称、归属均经过程序检查，工具数据不改变授权。
- [ ] 能关联任务、步骤和消息；脚本测试通过与真实模型质量通过分开记录。

## 9. 阶段 F：审批、暂停与恢复

预算：5～7 个学习日。目标是写操作经批准才能执行，能持久恢复并避免重复创建。
“进阶”表示拆到后面的学习单元，不表示可以删掉完整课程的验收要求。

### M16：先定义并实现审批业务（原第 16 课）

- 问题：助手提出创建工单时，用户批准的究竟是哪一次操作、哪些参数？
- 先修：M12 的幂等、M13 的权限与 Schema、M15 的任务记录。
- 起步：给出一份固定工单草稿，手动走“待审批 → 批准/拒绝”，先不依赖 LangGraph。
- 位置：拟新增审批记录、创建工单 Service、审批接口与前端参数确认区。
- 分步任务：
  1. 明确只读与写操作区别，保存待执行参数快照、操作 ID、归属和审批状态。
  2. 展示执行摘要，实现 approve/edit/reject；编辑后的参数重新校验并记录。
  3. 首次接通创建工单就校验审批权限，并使用稳定操作 ID 去重；只生成新 ID 不能防重。
  4. 拒绝、未批准、过期或无权的请求不执行，旧审批不能应用于新工具调用。
- 正常/失败：批准后创建一个工单；未批准、被拒绝、无权和重复提交不产生额外工单。
- 完成证据：审批参数与实际执行可对应；此时若尚不能重启恢复，明确记录该能力未完成。

### M17：从小状态图到持久化暂停恢复（原第 17 课）

- 问题：流程暂停等待人决定之后，怎样在之后甚至重启后继续？
- 先修：M16；先讲状态、节点、边及状态传递，不直接从持久化框架配置开始。
- 起步位置：拟新增 `learning/approval_graph.py`。先用不写数据库、不调用外部服务的
  “准备草稿 → 暂停 → 返回结果”小流程观察状态，再接入 LangGraph。
- 分步任务：
  1. 先画图并完成内存里的暂停与继续，解释 checkpoint 是可恢复执行快照。
  2. 运行与锁定版本匹配的 `interrupt/resume` 示例，观察恢复时哪些代码可能重跑。
  3. 在业务设计中补等待审批状态，明确拒绝、取消、过期及恢复后的状态转换。
  4. 接入 PostgreSQL Checkpointer，将会话对应到 `thread_id`，校验查看审批与恢复的身份。
  5. 服务重启后展示同一待办并继续，确认审批没有串到别的调用。
- 正常/失败：合法身份可恢复；其他身份不可查看或恢复；取消或过期后不能被旧请求继续执行。
- 完成证据：内存示例与持久化重启实验分别记录；只做内存暂停不标记本模块完成。

### M18：验证重放与工单去重（原第 18 课）

- 问题：恢复过程重跑部分代码，或工单已创建但流程未记完，怎样不重复写入？
- 先修：M17、M12；复习副作用、稳定操作 ID、唯一约束与事务边界。
- 起步：用同一个操作 ID 调用 M16 的创建逻辑两次，确认返回同一工单。
- 位置：工单/审批 Repository、恢复协调逻辑和故障测试。
- 分步任务：
  1. 恢复时查已有操作结果，明确何时复用工单、何时需要核对。
  2. 测试重复批准、两次并发恢复，检查数据库级去重。
  3. 在“工单已创建但流程完成尚未记录”的位置模拟中断，再恢复。
  4. 写清业务表与 Checkpointer 各自保存什么，以及不一致时的发现和处理流程。
- 正常/失败：同一批准操作只对应一张工单；不确定结果进入明确核对状态，不能盲目再创建。
- 完成证据：崩溃窗口测试与恢复说明；能解释保存 checkpoint 为什么不自动保证副作用只发生一次。

阶段 F 验收：

- [ ] 批准、编辑后批准、拒绝有演示与测试；权限校验随写操作一起生效。
- [ ] 重启后待办仍在，另一身份不能审批或恢复，旧审批不能用于新调用。
- [ ] 重复批准、并发恢复与创建后中断有验证；暂停前重跑的代码具有必要的幂等保护。
- [ ] 工单、审批、Run 与执行快照的职责和不一致恢复方式写清楚。

## 10. 阶段 G 前半：测试、追踪与质量评测

本节与第 11 节合计预算 5～7 个学习日。基础日志与测试从前面持续使用，这里整理完整链路。

### M19：建立可定位问题的执行记录（原第 19 课）

- 问题：一次请求失败后，怎样查到是哪个执行步骤失败？
- 先修：M15 的 Run/RunStep；先把已有错误输出改为结构化字段，再扩展关联。
- 起步：用一条模拟订单任务，列出 `requestId`、`conversationId`、`runId`、`stepId` 的对应。
- 位置：现有请求 ID 中间件、执行与工具日志、相关记录查询入口。
- 分步任务：统一字段 → 记录首片/总耗时与工具耗时 → 关联步骤 → 按一次工具超时排查。
- 正常/失败：正常任务的记录可串联；失败能定位步骤和用户反馈，并发任务不会混淆。
- 完成证据：一份排查记录；日志不记录密钥或完整认证头，用量缺失有明确标识。

### M20：按风险整理测试并补端到端流程（原第 20 课）

- 问题：哪些测试证明纯逻辑、接口、数据库或用户操作，哪些风险仍未覆盖？
- 先修：各阶段已写的测试；首次使用浏览器自动化前先提供最小运行例子与启动命令。
- 起步：把已有测试按层列清单，选择一个实际缺口，不重复测试相同实现细节。
- 位置：Server/Web 测试目录及拟新增的 E2E 目录。
- 分步任务：核对解析/上下文/状态机 → 核对归属/审批/幂等 → 补页面行为 → 增加 Mock 端到端流程。
- 正常/失败：发送、增量、停止、再次发送、查看历史可复现；服务或工具失败时界面能收尾。
- 完成证据：能区分未覆盖、Mock 编排通过和真实模型质量通过；数据库测试与正常学习库隔离。

### M21：从小样本开始建立 Eval（原第 21 课）

- 问题：接口都正常时，怎样发现模型理解或工具选择仍然不符合预期？
- 先修：M14 的工具过程与 M20 的测试边界；先解释固定案例、预期行为和评分规则。
- 起步：先做直接问答、查订单、拒绝越权三例，再扩展到约 20 例。
- 位置：拟新增评测案例文件与运行脚本，开课时明确文件格式、命令和报告位置。
- 分步任务：定义输入/模拟数据/预期工具参数/禁用行为 → 执行并分类失败 → 修改一次提示词 → 对比基线。
- 正常/失败：涵盖缺参数、查不到、无权限、工具失败和审批；重点评估行为与事实，不要求自然语言逐字相等。
- 完成证据：报告成功率、失败案例、改善与退化，记录模型/提示词版本、日期和重复次数。
- 边界：Mock 验证规则与评测流程；真实模型评测单独显式启用并设预算，不进入默认自动化。
  小样本结果不包装成生产准确率保证；提示词或工具改变后可重跑同一组案例。

## 11. 阶段 G 后半：工程检查、部署与演示

### M22：整理工程检查入口（原第 22 课）

- 问题：怎样让另一台机器或 CI 自动发现常见问题？

- 完成证据：每条命令覆盖清楚，CI 不依赖个人模型密钥；`compileall` 不是类型检查。

### M23：可复现部署与配置（原第 23 课）

### 14.2 第一份作业：一次请求与响应

这份作业属于 D01。目标是观察请求与响应，不要求修改业务代码或编写 Python 测试。
若环境准备遇到问题，先学习并解决启动问题，再做本作业，不把环境失败当成学习者能力不足。

**准备。** 在 Windows PowerShell 进入仓库并检查已有修改：

```powershell
Set-Location 'C:\Code\GitHub\boring-ai-platform'
git status --short
```

首次安装依赖才执行下面两条命令；依赖已装好且锁文件未变时跳过。
缺少 Node、pnpm、Python 或 uv 时，先按 README 与带学者提供的步骤安装并验证版本。

```powershell
pnpm install --frozen-lockfile
uv sync --project apps/server
```

本次学习用两个终端分别启动服务，明确让 Server 继承 Mock 设置。
终端 A 留在仓库根目录，执行：

```powershell
$env:AI_PROVIDER = 'mock'
pnpm --filter @repo/server dev
```

再打开终端 B，进入同一仓库后启动 Web：

```powershell
Set-Location 'C:\Code\GitHub\boring-ai-platform'
pnpm --filter @repo/web dev
```

这个环境变量设置只影响终端 A 及其启动的进程，不需要填写模型密钥。
保留两个终端；浏览器打开默认 Web 地址 `http://127.0.0.1:5173`。
若配置过其他端口，以启动输出为准。默认 Server 为 `http://127.0.0.1:3001`。

**先观察成功。** 打开开发者工具的 Network，选择 Fetch/XHR，再在聊天页发送一条“你好”。
找到 `/api/v1/chat/messages` 请求，分别查看请求信息、Payload 和 Response。

记录以下四项即可：

1. 请求方法与地址。
2. 请求体里表示这次输入的字段和值。
3. HTTP 状态码，以及响应里表示助手回复的字段和值。
4. 响应中的哪段文字出现在页面上。

提示：请求体找 `content`；成功响应的助手文字位于 `data.message.content`。
预期 HTTP 为 `200`，Mock 回复包含“Python 服务端已收到：你好”。看不到请求时，先检查 Network
是否在录制、筛选条件是否正确、页面有没有真正提交；不需要先去修改后端。

**审查后再观察失败。** 先把成功记录贴给带学者解释。随后在同一浏览器的新标签访问
`http://127.0.0.1:3001/api/v1/learning-not-found`，在该标签的 Network 中选择 All 查看请求。
预期为 `404`，JSON 中的 `msg` 表示接口不存在，`data` 含请求 ID。
这个地址是有意选取的不存在接口，用来理解错误响应，不是待修复的迁移缺陷。

提交格式：四项成功记录，加一句成功与错误响应的区别。初次作业可以只交观察记录；
后面有代码任务时才贴代码。只有实际结果不符，才按现象排查，不要求用代码补齐未知功能。

**完成标准。** 能解释“浏览器发送数据，后端返回结果，页面显示结果”，并识别一次成功和
一次明确的 HTTP 错误。通过后进入 D02；不跳过 Python 基础直接进入 SSE 或测试替身。
